## 1. 합성 대상과 방식
- **`rv32i_mcu`를 한 번에 합성(top-down)**하고 모듈 계층은 유지한다(`auto_ungroup none`) → `report_area`에서 모듈별 면적을 본다
  - 임계 경로가 코어 → 주소 디코더 → 메모리 → 코어로 모듈 경계를 여러 번 지나므로, 모듈별로 따로 합성해 합치면(bottom-up) 경로마다 시간을 나눠 정해야 하고 경계 최적화가 끊긴다. 이 크기(수천~1만 셀)에서는 한 번에 합성하는 쪽이 정확하고 간단하다
- 읽는 파일: 코어(`rv32i_core` + control, regfile, imm_gen, alu, branch_cmp, lsu — 대기(stall) 추가판), `bus_mux`, `apb_bridge`, `apb_gpio`, `apb_timer`, `apb_uart`, `rv32i_mcu`
- 빼는 파일: `mcu_imem`, `mcu_dmem`, `mcu_top` (시뮬레이션·FPGA 전용 — gpdk045에 SRAM 매크로가 없음)
- 목표 주기 **8 ns** (3단계와 같음) → 합성 6.4 ns. 클럭·여유 규칙은 [ch05 README 2절](../ch05_single_cycle/README.md)

## 2. 타이밍 제약 (SDC)
메모리 시간 모델은 3단계와 같다 (`T_ADDR` 0.5, `T_MEM` 1.0, `T_WB` **1.2**, `T_WSU` 0.3 ns) → 두 결과를 그대로 비교할 수 있다.
- `T_WB`는 처음 1.0 ns였다. 첫 합성에서 메모리 뒤 구간(디코더 읽기 MUX → lsu → WB → 레지스터 파일)이 주기와 관계없이 맞지 않아(5절), 메모리 시간은 그대로 두고 코어 시간의 앞뒤 몫만 옮겨 **1.2 ns로 재배분**했다. 3단계도 같은 값으로 다시 합성해 비교한다 ([ch05 README 2-1절](../ch05_single_cycle/README.md))

| 포트 | 제약 | 이유 |
|------|------|------|
| `imem_addr` / `imem_rdata` | 출력 `주기 − T_ADDR` / 입력 `T_ADDR + T_MEM` | 명령어 읽기 (3단계와 같음) |
| `ram_addr`, `irom_addr` / `ram_rdata`, `irom_rdata` | 출력 `T_MEM + T_WB` / 입력 `주기 − T_WB` | 데이터 읽기. DMEM과 IMEM 데이터 포트에 같은 예산 (주소 디코더를 지나는 시간은 코어 몫) |
| `ram_wstrb`, `ram_wdata` | 출력 `T_WSU` | 다음 에지에 쓰기 |
| ~~`apbx_*` (외부 APB 슬롯)~~ | (2026-11-12 삭제) 메모리와 같은 예산이었음 | 브리지가 `PSEL`·`PADDR`를 레지스터에 담지 않고 코어 주소에서 바로 내보냄 → 반 사이클을 주면 맞출 수 없음 |
| `gpio_out`, `gpio_oe`, `uart_tx` | 출력 주기 × 0.5 | 플립플롭 출력 → 패드·보드에 반 사이클 |
| `gpio_in`, `uart_rx` | `set_false_path` | 비동기 입력, 내부에서 2단 플립플롭으로 동기화 |
| `dbg_pc`, `trap`, `bus_err`, `timer_irq` | 출력 0 | 관찰·오류 신호 |
| `rst_n` | `set_false_path` | 비동기 리셋 |

- 3단계와 달라지는 경로: load의 주소가 **주소 디코더**를 거쳐 메모리로 가고, 읽은 값이 **디코더 MUX**(DMEM / IMEM / APB)를 거쳐 돌아온다. 또 `dmem_ready`(대기)가 PC·레지스터 쓰기 조건에 들어간다 → 같은 8 ns 안에서 코어 로직이 쓸 수 있는 시간이 조금 줄어든다
- APB 주변장치 내부 경로(브리지 상태 → `PSEL` → 주변장치 레지스터)는 칩 안이라 따로 제약할 것이 없다

## 3. 실행 (학교 서버)
`GPDK045_DIR` 설정은 [ch05 README 3절](../ch05_single_cycle/README.md)과 같다.

**(A) 일괄**
```bash
bash syn/ch14a_mcu/run_syn.sh
```
- 인자 = 목표 주기(ns), 기본 8 → 합성 6.4 ns. 결과 `syn/ch14a_mcu/runs/t8ns/`

bash syn/ch14a_mcu/run_syn.sh -i

## 4. 예상과 미리 확인한 것
- 이 PC에서 확인 (Genus 없이)
  - 스크립트를 Tcl 흉내 명령으로 끝까지 실행: 경로·주기(8 → 6.4 ns)·파일 목록 정상, SDC가 `rv32i_mcu` 포트 27개를 모두 제약
  - 합성 파일 목록만으로 `rv32i_mcu` 정교화(xelab) 성공
  - Vivado로 한 번 합성(Zynq-7000, 참고용): 래치·다중 구동 없음. 경고는 "쓰지 않는 입력 비트"(주변장치 `pwdata` 상위 비트, `paddr` 상위 비트, lsu 주소 상위 비트 등)뿐 → Genus에서도 같은 종류의 미사용 포트 메시지가 나올 수 있다
- 예상: 순차 셀 = 3단계 1,024개 + 주변장치·브리지 약 250개 (GPIO 16×2 + 동기화 32, TIMER 32×2 + 제어, UART 분주기·시프트 레지스터 등). 면적 증가는 주로 이 플립플롭과 APB 읽기 MUX

### 임계 경로 (8 ns 목표, 합성 6.4 ns, slack −0.168 ns)
```
apbx_prdata[23]  (입력 지연 = 6.4 − T_WB 1.0 = 5.4 ns)
 -> u_apb_bridge  슬롯별 PRDATA 선택 (NAND2 2단)            5.400 -> 5.543
 -> u_bus_mux     읽기 데이터 선택 DMEM/IMEM/APB (NAND2 2단) 5.543 -> 5.664
 -> u_lsu         바이트·하프워드 선택, 부호 확장             5.664 -> 6.024
 -> u_core        WB MUX -> 레지스터 31개로 분기(INV 팬아웃 31) 6.024 -> 6.250
 -> u_regfile regs_reg_*_17/D (EDFFHQX1, setup 0.219 + uncertainty 0.1) 요구 6.081
```
- 위반 끝점은 모두 **레지스터 파일**(약 1,000개). 최악 10개 경로가 모두 `apbx_prdata`(외부 APB 슬롯)에서 시작한다
- 원인: SDC는 메모리에서 돌아온 데이터에 `T_WB` = 1.0 ns를 준다(3단계와 같음). 3단계에서는 그 안에 lsu → WB MUX → 레지스터만 있었는데, MCU에서는 앞에 **디코더의 읽기 MUX**(약 0.12 ns)와, 외부 APB 슬롯이면 **브리지의 슬롯 MUX**(약 0.14 ns)가 더 붙었다
- 레지스터 파일 플롭이 쓰기 허용 플롭(EDFF)이라 setup이 0.219 ns로 커서 1.0 ns 중 실제로 쓸 수 있는 시간은 약 0.68 ns
- 다른 경로 종류(DMEM 데이터, 명령어 → 주소, 플롭 → 플롭)의 최악 slack은 이 리포트만으로 알 수 없어, STEP 7에 경로 종류별 리포트(`21_rv32i_mcu_path_classes.rpt`, [path_classes.tcl](path_classes.tcl))를 추가했다 → 다시 합성해 확인

### 경로 종류별 최악 slack (ps)
| 종류 | 8 ns (합성 6.4) | 8.5 ns (합성 6.8) | 주기를 늘렸을 때 |
|------|----:|----:|------|
| `in_apbx_to_reg` 외부 APB 데이터 → 레지스터 | −168 | −161 | 거의 그대로 |
| `in_mem_to_reg` DMEM·IMEM 데이터 → 레지스터 | −160 | −156 | 거의 그대로 |
| `in_imem_to_addr` 명령어 → 데이터 주소 출력 | −168 | −161 | (아래 설명) |
| `in_imem_to_reg` 명령어 → 레지스터 | −110 | −94 | (아래 설명) |
| `reg_to_imem_addr` PC → 명령어 주소 | +20 | +7 | |
| `reg_to_reg` 칩 안쪽 | +531 | +847 | 늘어남 |
| `to_mem_write` DMEM 쓰기 | +680 | +651 | |

- **데이터 → 레지스터 경로는 주기와 관계가 없다.** 입력 지연이 `주기 − T_WB`, 요구 시간이 `주기 − setup − uncertainty`라서 쓸 수 있는 시간은 항상 `T_WB − setup − uncertainty` ≈ 1.0 − 0.22 − 0.1 = 0.68 ns다. 디코더 읽기 MUX가 더해진 MCU의 이 구간(약 0.84 ns)은 주기를 아무리 늘려도 맞지 않는다
- 명령어에서 시작하는 두 종류는 주기에 따라 여유가 생겨야 하는데 거의 그대로다. Genus는 최악 slack(WNS)을 고칠 수 없으면 다른 경로를 그 수준까지 작은 셀로 바꿔 면적을 줄이므로(면적이 29,803 → 27,292 µm²로 줄어든 것과 같은 현상), 이 값은 실제 한계가 아니라 WNS에 맞춰진 값으로 본다 (리포트로 확인 필요)
